用AoE2ScenarioParser给官方战役开启256x科技

上篇改的是 AoE2DE\resources\_common\xs\x256tech.xs，那是共享脚本，所有引用它的场景都会跟着变。这次换一条路：不动共享脚本，只把 x256tech 这个脚本名写进单个场景文件，让游戏在加载这一关时把 256x 科技挂上，其他关卡不受影响。

以官方帖木儿战役第一关为例，全程只改一个字段。

官方战役的场景是打包的

官方战役的场景没有散落在硬盘上，全部打包在 AoE2DE\resources\_common\campaign\kcam1.aoe2campaign 里。从文件里能读出 K1_Tamerlane_1.aoe2scenario 到 K1_Tamerlane_6.aoe2scenario 六个文件名，后面跟着压缩过的场景数据。

所以不能只生成一个 .aoe2scenario 丢进 campaign 目录了事 —— 得先把这个场景从包里拆成独立文件，改完再重新打包回去。

场景靠 script_name 挂脚本

.aoe2scenario 的 Map 段里有个 script_name 字段，记录这个场景要加载的 XS 脚本名。官方这几关的这个字段是空的：用解析器读原文件，xs_manager.script_name 打印出来是 ''。空着就不带任何脚本。

填上 x256tech，游戏加载这一关时就会去 xs 目录找同名脚本，也就是 AoE2DE\resources\_common\xs\x256tech.xs —— 上篇那份只对玩家 1 生效的版本。

这也解释了这条路和上篇的关系：上篇是改脚本内容（谁生效），本篇是改引用（哪一关生效）。两件事正交，可以各改各的。

准备

  • Python 3（实测 3.14）+ pip install AoE2ScenarioParser（实测 0.9.8）
  • 把场景从战役里拆出来：游戏内 场景编辑器 → 战役编辑器，战役文件名填 kcam1，加载。拆出来的场景落在用户目录：

帖木儿战役是六关，这里会看到 K1_Tamerlane_1.aoe2scenario 到 K1_Tamerlane_6.aoe2scenario。

  • 把第 1 关复制一份、改名成 K1_Tamerlane_1.aoe2scenario.bak 当原件备份 —— 脚本读 .bak、写 _，原件不动。

改

三行各干一件事：

  • from_file 把整个场景解析进内存，地图、单位、触发器全在里面（这一关是 42 个触发器）。
  • xs_manager.script_name 直接对应 Map 段的 script_name 字段，写脚本名、不带 .xs 后缀。
  • write_to_file 重新序列化落盘。

写出来的文件比原件小：59,741 → 55,797 字节。这不是丢内容，是解析器按自己的结构把场景重写了一遍，触发器、单位都在。要确认改动生效，读回来打印一眼：

重新打包

游戏内 场景编辑器 → 战役编辑器：加载 kcam1，把第 1 关的位置换成刚生成的 K1_Tamerlane_1_.aoe2scenario（用 添加/删除 调整场景列表），保存成 kcam1.aoe2campaign。编辑器保存到用户目录：

再复制到游戏目录覆盖：

覆盖前先备份游戏目录里的原件。实测原始 kcam1.aoe2campaign 是 373,474 字节，重新打包后 369,530 字节，小了 3,944 —— 正好等于第 1 关场景重写后小掉的 3,944 字节，包里只动了这一关。

然后进战役 → 帖木儿 → 第一关，科技可以重复研究了。

另一条路：把脚本直接塞进场景

解析器还有个 xs_manager.add_script()：它把整段 XS 文本写进一个 Script Call 效果，游戏启动时落到用户目录的 xs\default0.xs 里。好处是脚本跟着场景文件走，对方没有 x256tech.xs 也能生效；代价是脚本内容进了场景二进制，还多一个触发器。

这里只是引用现成的 x256tech.xs，自己单机玩，用 script_name 更省事。要分享给别人、或者做联机（观战端拿不到本地脚本文件），add_script 才是稳的那条。

没生效先查这几处

  • resources\_common\xs\x256tech.xs 是否还在。脚本名和文件名要严格对上，注意 script_name 里不带扩展名。
  • 覆盖的是游戏目录那份 kcam1.aoe2campaign，不是用户目录那份。游戏读的是资源目录。
  • 场景里真的写进去了没：读回 K1_Tamerlane_1_.aoe2scenario 打印 script_name。
  • 游戏更新或 Steam 校验文件会还原 resources 下的东西，覆盖后又被还原的话，表现就是「什么都没发生」。
  • 上篇提过的坑这次仍然适用：如果 x256tech.xs 里 xsGetPlayerNumberOfTechs 传的是未赋值的 player，遍历范围不确定，两处都写死 1 才干净。

小结

  • 官方战役场景打包在 .aoe2campaign 里，改一关要走「拆包 → 改场景 → 重新打包 → 覆盖游戏目录」。
  • 让某一关带 256x，只需要把场景 Map 段的 script_name 写成 x256tech，一条赋值就够。
  • 这条路粒度是单个场景：不影响其他关卡，也不改动共享脚本；但脚本文件本身仍要放在 xs 目录。
  • 解析器写出的场景文件会比原件小几千字节，属正常重写，不是内容丢失。
  • 备份留好，游戏更新会还原 resources 下的文件。

帝国时代2决定版修改x256玩家生效

帝国时代2决定版里的 x256 科技模式（同一项科技可以叠加研究 256 次）是靠 AoE2DE\resources\_common\xs 下的 XS 脚本打开的。默认脚本对所有玩家都打开叠加，改动的目的则是让 x256 只对玩家 1 开放，其他玩家维持原版科技。

改动前记得先备份原文件，Steam 校验文件或游戏更新都会把它覆盖回去。

原脚本

这段脚本遍历 1 到 xsGetNumPlayers() 的每个玩家，把该玩家科技列表里每一项科技的 stacking 属性设为 1。stacking 就是「这项科技可以叠加」，xsEffectAmount 的最后一个参数决定这次改动写到哪个玩家的科技表上。所以按原版走，每个玩家都能把科技叠到 256 次。

改后

改动三处：

  • 删掉外层玩家循环，不再逐个玩家遍历；
  • xsEffectAmount 的玩家参数写死为 1，属性只写进玩家 1 的科技表；
  • 内层循环的 xsGetPlayerNumberOfTechs 也传 1，不再传 player。

改完保存，重启游戏进局，只有玩家 1 的科技可以重复研究。

两处都得写死 1

这两处不是重复劳动，各自管一件事：

  • xsEffectAmount(..., 1, 1) 的最后一个 1 决定把 stacking 写到谁的科技表上，写死它，其他玩家就拿不到叠加；
  • xsGetPlayerNumberOfTechs(1) 决定遍历多少项科技，传玩家 1 才是玩家 1 的科技列表范围。

第二处容易漏。player 原本靠外层循环赋值才有值，循环删掉之后没人给它赋值，它的值就取决于同一运行环境里其他脚本残留的同名全局变量 —— 可能是 0，也可能是别的玩家的编号。留着它，遍历范围就变成不确定的，限制也就不干净：极端情况下会按别人的科技数量去给玩家 1 写属性。两处都写死 1，脚本行为才不依赖任何外部变量，换地图、换场景结果一致。

适用范围

这份改动是「只给自己开」的用法：

  • 单机、只关心玩家 1 的科技时，这就是想要的效果；
  • 多人对局里其他玩家拿不到叠加，属于预期行为，不是 bug；
  • 如果哪天想反过来让所有玩家都吃到 256x，那就把外层玩家循环恢复回来，把玩家号同时传给 xsGetPlayerNumberOfTechs 和 xsEffectAmount 两处。

小结

  • 直接改 AoE2DE\resources\_common\xs 下的脚本，改完重启游戏生效，注意备份。
  • 让 x256 只对玩家 1 开放的关键：xsEffectAmount 的玩家参数和 xsGetPlayerNumberOfTechs 的参数都固定为 1。
  • 删掉外层循环后 player 失去赋值来源，必须一并替换掉，否则遍历范围会跟着全局变量漂移。

从阿里云迁移域名到 Cloudflare 并部署临时邮箱

这篇文章把几份分散的部署说明整理成一条完整路径：先把阿里云注册的域名交给 Cloudflare 托管 DNS，再用 Cloudflare D1、Workers、Email Routing 和 Pages 搭建一个可收信、可管理、可访问的临时邮箱系统。整体顺序建议不要颠倒，尤其是域名和 Email Routing，它们决定邮件能不能真正投递到 Worker。

阿里云迁移域名

这里的“迁移”重点不是把域名注册商从阿里云转出，而是把域名的 DNS 解析权交给 Cloudflare。域名依然可以在阿里云续费和管理所有权，但解析记录、邮件路由、Workers 自定义域名等能力交由 Cloudflare 控制。

第一步是在 Cloudflare 控制台添加站点，输入你在阿里云购买的根域名，例如 example.com。Cloudflare 会扫描现有 DNS 记录，扫描结果只能当作参考，最好和阿里云 DNS 解析列表逐条核对，确保 A、AAAA、CNAME、MX、TXT 等记录没有遗漏。确认记录后选择合适套餐，个人项目通常从 Free 计划开始即可。

第二步回到阿里云域名控制台，找到域名的 DNS 服务器设置，把原来的阿里云 DNS 服务器替换为 Cloudflare 分配的两条 nameserver。修改后等待全球 DNS 生效，Cloudflare 控制台会在检测通过后显示站点已激活。这个等待过程可能从几分钟到数小时不等，期间不要频繁来回切换 DNS 服务商，否则排查会变得很混乱。

第三步是在 Cloudflare 中重新检查解析结果。网站访问、邮箱投递、后端 API、自定义 Pages 域名都依赖 DNS，因此建议先确认根域名和需要使用的子域名都已经在 Cloudflare DNS 中存在。后续如果要把 temp-api.example.com 绑定到 Worker，或把 mail.example.com 用作前端页面，都应该提前规划清楚。

初始化/更新 D1 数据库

D1 是这个临时邮箱项目的数据层，用来保存邮箱地址、邮件内容、用户和管理配置等信息。进入 Cloudflare 控制台后，依次选择 Storage & Databases、D1 SQL Database、Create Database 创建数据库。名称可以按项目命名，例如 temp-mail-db，方便后续在 Worker 绑定时识别。

创建完成后需要初始化表结构。进入该 D1 数据库的 Console 标签页，把项目仓库中的 db/schema.sql 内容粘贴进去并执行。文档也提到，如果暂时跳过初始化，可以在部署完成后进入 admin 页面的 快速设置、数据库，再点击 初始化数据库，但我更建议在 Worker 正式接流量前先完成初始化，这样后面验证接口时更直观。

后续升级项目时，要关注项目更新日志。如果版本变更涉及 schema，需要找到对应的 patch SQL，例如类似 db/2024-01-13-patch.sql 这样的文件，再到 D1 的 Console 中执行。不要重复执行不确定的补丁，也不要跳过跨版本 patch；数据库结构和 Worker 代码版本不一致时，前端很容易出现接口异常或初始化失败。

Cloudflare workers 后端

Workers 是整个系统的后端入口，负责接收 Email Routing 投递过来的邮件，也提供前端和 admin 页面需要调用的 API。进入 Cloudflare 控制台，依次选择 Compute (Workers)、Workers & Pages、Create，选择 Worker 并创建一个新 Worker。创建后先部署默认代码，确认 Worker 项目存在。

接着进入 Worker 的 Settings、Runtime，添加 nodejs_compat compatibility flag，并确保兼容日期满足项目要求。这个步骤很关键，如果缺少 Node.js 兼容能力，上传正式 worker.js 后可能遇到 path、node:stream 等模块相关错误，前端也可能只看到笼统的 Network Error。

然后从项目发布页下载最新的 worker.js，进入 Worker 的在线编辑器，删除默认文件并通过 Explorer 上传 worker.js，再点击 Deploy。上传完成后需要配置环境变量和绑定资源：

  • 在 Variables and Secrets 中配置 DOMAINS、JWT_SECRET、ADMIN_PASSWORDS、ENABLE_USER_CREATE_EMAIL、ENABLE_USER_DELETE_EMAIL 等变量。
  • DOMAINS 用 JSON 数组填写所有可用邮箱域名，例如 ["example.com","mail.example.com"]。
  • D1 绑定名必须是大写 DB，并选择前面创建的 D1 数据库。
  • 如果启用注册用户邮箱验证，需要创建 KV 命名空间并以大写 KV 绑定到 Worker。
  • 如果使用 Telegram Bot，额外添加 TELEGRAM_BOT_TOKEN。
  • 如果希望 admin 中的邮件清理定时任务生效，需要在 Trigger Events、Cron Triggers 中添加 Cron，例如 0 0 * * *。

最后进入 Settings、Triggers 为 Worker 添加自定义域名，或者先使用 Cloudflare 自动生成的 *.workers.dev 域名测试。考虑到 workers.dev 在国内访问不稳定，正式使用时更推荐绑定自己的 API 域名。部署完成后，依次访问 Worker 根路径、/health_check 和 /open_api/settings：前两个返回 OK，后一个返回 JSON，说明后端基础状态正常。

Cloudflare Email Routing

Email Routing 是收件能力的核心。即使 Worker 和 Pages 都部署成功，只要 Email Routing 没有配置好，临时邮箱仍然收不到验证码或邮件。

在 Cloudflare 的对应域名下进入 Email Routing，先启用 Email Routing，并按照控制台提示添加电子邮件 DNS 记录。通常 Cloudflare 会提示需要配置 MX 和 TXT 等记录，如果域名 DNS 已经托管到 Cloudflare，这些记录可以直接由控制台下发或确认。多个域名要分别配置，不能只配置其中一个。

启用 Email Routing 前还需要至少有一个已验证的目标邮箱地址。这个目标邮箱用于 Cloudflare 邮件路由的基础校验；等 Worker 部署完成后，再把路由规则中的 Catch-all 地址 指向 Worker。Catch-all 的作用是让任意前缀的收件地址都能进入临时邮箱系统，例如 abc@example.com、test@example.com 都可以被 Worker 处理。

如果使用子域名收信，例如 mail.example.com，必须对这个子域名单独启用 Email Routing，并配置对应的邮件 DNS 记录和 Catch-all 规则。父域名的 Email Routing 不会自动覆盖子域名，也不会让子域名继承邮件投递规则。

Cloudflare Pages 前端

Pages 用来部署临时邮箱的前端页面和 admin 管理页面。进入 Compute (Workers)、Workers & Pages、Create，这次选择 Pages，再选择 Use direct upload。

前端包里需要写入后端 API 根地址。可以使用文档页面提供的生成方式，也可以手动下载 frontend.zip 后修改其中的 assets/index-xxx.js 文件，把占位地址 https://temp-email-api.xxx.xxx 替换为你的 Worker API 根地址。这里一定要填后端 API 域名，例如 https://temp-email-api.example.com，不要填 Pages 前端域名，也不要带 /admin、/api 或结尾 /。在上传前，建议先打开 https://你的-worker-api域名/open_api/settings，确认返回 JSON。

上传 zip 包创建 Pages 项目时，要在高级选项里把未找到处理设置为 Single-page application (SPA)。这个项目是单页应用，如果不启用 SPA 模式，直接刷新 /admin 等子路径时可能返回 404。

部署完成后，打开 Pages 默认的 *.pages.dev 地址确认页面能访问，再根据需要进入 Custom Domain 添加自己的前端域名。为了避免缓存影响，如果第一次填错 API 地址后重新部署仍然报错，可以用无痕窗口测试或清理浏览器缓存。

小结

整套流程可以理解为：阿里云域名把 DNS 控制权交给 Cloudflare，D1 保存数据，Worker 承担后端和收件处理，Email Routing 把邮件投递给 Worker，Pages 提供用户界面。排错时也按这个链路反向检查：前端报错先看 /open_api/settings，收不到邮件先看 Email Routing 和 DNS，数据库相关异常则看 D1 初始化和 Worker 的 DB 绑定名。
